# 踩坑清单

每条都是本项目真实踩过的。按「什么时候会踩」分组。

---

## A. 设计阶段

### 1. 用分数/分差分桶，是错的

**原方案**：按 spread（最高分−最低分）分桶再人工复核。
**全量试跑前 47 条就否掉了**：分差大不等于题目有筛选力——大量题是「模型都答对了，只是有的写得深有的写得浅」，spread≥2 却毫无价值；而「所有模型全部中了同一个谄媚陷阱」这种最硬的共性弱点，因为分数都不低**反而被漏掉**。

改为按「实质答错的模型数」判定。**这是整个项目最贵的一次口径修正，如果全量跑完才发现就要全部重跑。**

### 2. judge 是被评模型之一 = 结果作废

self-preference bias 是硬约束。本项目早期 42 条 + 100 条小样本和前 16 批用的是另一个 judge 模型，口径调整后**那批结果整批作废重跑**，不进入最终产出。每份结果文件顶层记 `judge_model`，就是为了这种时候能一键筛出该重跑的批次。

### 3. reference_answer 只给「具体答案 / null」两态，judge 会编

深度知识题上，judge 被迫二选一时会**自信给出未经核实的错误答案**。必须加第三态：「需要外部核查但我核不了」→ `reference_answer=null` + `verification_needed` 列出具体事实点。

### 4. 把多种性质的现象塞进一个字段，统计会失真

原先单一 `trap_check` 混了事实性陷阱、社会性讨好、指令冲突三种完全不同的东西，导致「识破分歧率」虚高。拆成三个独立字段后才发现：**谄媚识破率跨度 35pp，事实类仅 20pp**——谄媚才是最能区分模型的那一类。混在一起时这个结论根本看不出来。

同理 `factual_trap` 单一布尔要拆成 `frame_recognized` + `content_correct`，否则「识破了框架但数字错」和「识破了表层、漏掉深层」无法区分。

## B. 执行阶段

### 5. 并发 agent 的临时文件会互相覆盖

多个 judge 子 agent 共享同一个 `tmp/` 目录。用 `step1.json`、`noanswers.json` 这类通用名，会被同级 agent 覆盖，**导致读到别的批次的题**——而且不会报错，结果看起来完全正常。

**规则**：临时文件名必须带批次号；读回后核对文件里的 id 与本批次一致，不一致立即重新提取。

### 6. agent 报 failed ≠ 工作丢失，但也 ≠ 工作可信

本项目 3 个批次的 agent 报了 failed，结果文件其实都写完了。**先跑校验再决定重不重跑**——直接重跑浪费，直接采信危险。

### 7. rubric 会把错误答案写死

至少 3 例：judge 写的参考答案本身就是错的，后续所有打分都建立在这个错答案上，且**内部完全自洽**、校验脚本查不出来。

**改判时的动作顺序**：先看 rubric 本身对不对，再看打分。不要一上来就调分数。

### 8. 译文里的专名可能是原文的手误

某题译文作「兰萨王国」，judge 写了检查项「妥当处理这一无从查证的指称」。回原文（葡萄牙语）看是 `o reino da rança`——`França`（法国）掉了首字母 F。**三家读懂手误按法兰西作答才是正确的**，唯一「指出该王国不见于任何地图」的那家反而没认出来。整条检查项建立在译文把手误固化成专名之上。

**规则**：写 Step 1 前先对照原文题面。译文里出现不认识的专名 → 回原文看是不是拼写手误。

### 9. 考语言形式的题，用译文回答评分等于考点消失

某题要求译成「自然流畅的英语」，模型交付 `"Do you have any backups handy?"`，译文回译成中文「你手头有备份吗？」——**要评的那句英文已经不在了**。另一题考俄语 `также`（连写）与 `так же`（分写）之辨，中文译文把两者都作「也」，考点直接消失。

**规则**：语言能力类题目，Step 2 以原语种回答为准。

### 10. 检查项引申得比题面更细

`source==explicit` 的 FAIL 直接计答错、直接决定入选，所以引申一句就能凭空造出一道入选题。

> 落地例：judge 把「每项分别给出工时费与配件费」标为 explicit，三家因合并报价 FAIL，`n_wrong=3` 触发入选。人工裁定改判 implicit——原文虽点名两类费用但未要求拆栏，且用户明确说「不要写太多」。改判后 `n_wrong` 归零。

## C. 复核阶段（本项目问题最集中的阶段）

### 11. 「只核实 judge 点名的事实点」会失灵

`verification_needed` 是 judge 自己列的——**judge 不知道自己错在哪**，指不到那里。已见 3 例「judge 视野之外的全员错误」：所有模型都错了同一件事，judge 也跟着错，于是 `verification_needed` 里根本没有这一项。

**规则**：核实不能只沿着 judge 给的清单走，要独立看题。

### 12. judge 判定方向整个反了

至少 5 例：judge 判「A 对 B 错」，实际是「B 对 A 错」。这类错误**不会被任何机械校验捕捉**——所有字段都自洽，只是内容反了。只能靠人工抽样看实质内容。

### 13. 单向复核 = 系统性偏高

只跑「可能改判入选」的类别，结果只会往上走。本项目入选数轨迹：

```
254  →  B 类复核 +25  →  峰值 281  →  A 类更正 −1、unresolved 处置 −5  →  274
```

如果只跑 B 类会停在 279，**系统性偏高 5 道**。任何复核批次都要同时包含可能升和可能降的样本。

### 14. 改判入选后不重跑去重扫描

最初的全库去重扫描只覆盖「**当时**已入选」的题。复核阶段翻上来的两道题里有重复的（洗车、棍子穿门），因此漏网——**是用户发现的，不是脚本发现的**。

**规则**：任何把题从淘汰改判入选的动作，都必须重跑全库去重扫描。无例外。

### 15. 拿今天的日期去翻案

时间锚点是**数据采集时点**，不是核实当天。本项目锚点 2026-03-06（uid 前缀 `log_26_0306`）。票价、在售状态、版本号、「最新款」这类题，用核实当天的事实去判，会制造出一批假错误。

## D. 数据质量与交付阶段

### 16. 字段里的「兜底桶」

本项目 `语种` 字段的 `en` 是兜底桶——检测器认不出的、含代码/公式/URL 的样本都被填成 en。全库修正 90 条，其中 84 条出自 en。

**修正后结论才成立**：英语入选率 13.2%（低于全库平均 18.3%）、**俄语才是入选题第一大语种**（29.3%）。修正前这两条都看不出来。

**规则**：出任何按字段分组的统计前，先查这个字段有没有兜底桶——看某个值是不是异常地大。

### 17. 分类字段混了多条分类轴，逐条改也改不出一致结果

本项目 `domain` 的 15 类里混了 5 种分类轴（主题领域 / 冷门程度 / 地域绑定 / 题目构造方式 / 任务性质）。对 276 道入选题逐条复核，初筛报 5 条错标，回原文后 **4 条被推翻**——`专业知识:建筑机械·工程标准` 是复合标签，机械件与技术规范类落进去**都合法**。

错标的根因是轴冲突，不是标注马虎。**决定不改，并在文档里写明原因和给下批数据的分类体系建议。** 明知改不出一致结果还硬改，是在制造新的不一致。

### 18. 交付层留空白 vs 伪造判定痕迹

没走过判定流程的行（第一轮就剔除的），交付表里**不能留空白**（协作方会以为漏标了），但也**不能填判定字段**（等于伪造判定痕迹）。

**做法**：结论类字段补齐（是否入选 / rejection_type / 理由 / stage_status），量化判定字段一律留空，并在产出说明里写清这批行的来源。

### 19. 回填脚本必须幂等 + 回读比对

判定会反复改。回填脚本要做到：dry-run 默认、`--write` 才落盘、落盘前自动备份、写完**逐字段回读比对**。本项目最终回填后做过全表 1510 行逐字段回读，`ERRORS: 0` 才算完成。

---

## 一句话总览

| 阶段 | 最容易出的错 |
|---|---|
| 设计 | 用分数/分差当判据；字段设计把多种现象塞一起 |
| 执行 | 并发文件覆盖；rubric 建立在错译/错答案上 |
| 复核 | 只沿 judge 给的线索核实；单向复核；改判后不重扫 |
| 交付 | 兜底桶字段没查；分母没写清；空白与伪造二选一 |
