# LLM-judge 评估集筛选

一套经 1510 条真实数据全量跑通的筛选流程（229 批 LLM-judge + 人工复核 + 联网核实 + 交付）。
本文是骨架与硬纪律；细则在 `references/`，可直接改造的脚本在 `scripts/`。

## 什么时候用

- 手上有一批「query + 多个模型的回答」，要从中选出**有筛选力的题**（能区分模型强弱的、暴露共性弱点的）
- 要设计一个批量 LLM-judge 流程，而不是人工逐条看
- 要复核别人（或自己上一轮）的 judge 结果，怀疑口径有问题
- 要向协作方解释「这个数字怎么来的」

**不适用**：单条 query 的临时质量判断（杀鸡用牛刀）；不涉及多模型对比的纯人工标注。

## 流程骨架：两道门，必须分开

```
全量数据
   │
   ├─ 第一轮：query 质量门 ──────► 只判「题目能不能被读懂、意图能否唯一确定」
   │   quality_flag                 不判难易、不判模型对错
   │   └─ 缺陷 → 剔除，第二轮字段全部留空（不是填 0，是留空）
   │   └─ 敏感 → 保留，但走人工路径
   │
   └─ 第二轮：区分性门 ──────────► 只判「模型表现是否分化」
       Step 1 出 rubric（不看回答）
       Step 2 逐模型打分（复用同一 rubric）
       Step 3 按 n_wrong 判入选 + 写理由
```

**为什么必须分开**：混在一起会让「题目不好」和「模型答不好」互相污染。第一轮判「所有模型都错」不是 query 缺陷——那是第二轮最有价值的信号（共性弱点）。

## 十条硬纪律

违反任何一条，结果就不可信。按重要性排序：

**1. judge 不能是被评模型之一。**
自评存在 self-preference bias，是硬约束。理想情况 judge 应比所有候选模型更强；底线是「可调用范围内最强、且不在候选名单里」。每份结果文件顶层记 `judge_model` 留痕。

**2. rubric 必须在看到任何回答之前写完，且靠机制保证、不靠自律。**
落地做法：用脚本只提取题面字段导出临时文件，judge 先只读它完成 Step 1，之后才允许读 answers。读过回答之后 **Step 1 任何字段都不得再改**——包括 `source` 的 explicit/implicit 标注，它直接决定入选结论，事后调它等于事后改结论。发现标错了：照原样打分，把「哪一项、原标什么、应标什么、改了结论会怎样」写进 `judge_note` 交人工裁定。

**3. 分数不是质量指标，分差也不是。判定依据只有 `n_wrong`。**
`score` 与事实正确性几乎不相关（实测 5+ 例：编造事实的模型分数反而更高），**不可用于排序、分层或任何质量指标**。

分差（spread）建立在 score 之上，继承同样的不可靠，因此**完全退出判定链**——不是降级成次级判据，四关判定里没有任何分支会因 spread 改变结论。三条实测：

- spread 大有三种成因，只有一种有价值：一家掉下来（孤例）、深浅差异（伪分歧）、真分化。单模型孤例题里 41% 的 spread≥3，但其余各家**内部**分差为 0 或 1 的占 87.5%——大 spread 完全由一家拉低下限造成，题目没有分层能力。
- 反方向同样失灵：「所有模型都中同一个谄媚陷阱」这种最硬的共性弱点，分数都不低、spread 极小，按 spread 排序会直接漏掉。原方案就是这么漏的。
- 因此「孤例 + spread 大」不构成例外通道，见纪律 4。

**但 spread 不删**：照常计算落表，用途是人工复核的**排序线索**与后续口径调整的追溯依据。「优先看哪些题」可以用它，「这题选不选」不能用它。同类处理的还有 `trap_divergence`、`explicit_check_count`——统称参考量，与判定字段在表里分区标注。

**4. 单模型孤例一律淘汰，错得再离谱也淘汰。**
`n_wrong == 1` → 其余模型都答对，说明题目本身不难；那一家的疏漏说明的是**那个模型**的问题，不是题目有筛选力。本项目对「孤例 + spread≥3 + 含幻觉」的 49 题明确拒绝开例外通道，实测支撑见 `references/stats-discipline.md`。

**5. 检查项要贴着题面原话写，不许引申得更细。**
题目说了 A，**不等于**要求「逐项 A」「分栏 A」「按某格式 A」。把推想出来的 A′ 标成 explicit，等于替用户加了一条他没提的要求，而 explicit 项 FAIL 直接计答错、直接决定入选。每条检查项只考一件事，不写复合项。

**6. 模型客观做不到的事，不算模型弱点。**
判答错前先问：这件事在本任务的客观条件下模型有没有可能做到？无检索能力的模型面对「必须实时核验才能负责任交付」的请求（有效链接清单、当前票价、此刻库存），退回到「说明无法核验 + 给检索路径」是**正确应对**。反之，**假装已完成核验**属幻觉，照常计答错。

**7. 复核必须双向做。**
只跑「可能改判入选」的类别 = 单向筛选 = 系统性偏高。本项目入选数轨迹 254 → 281（只升）→ 274（双向后），差 7 道全是单向偏差。任何复核批次都要同时包含「可能升」和「可能降」的样本。

**8. 任何改判入选的动作，必须重跑全库去重扫描。**
最初的去重扫描只覆盖「当时已入选」的题，后续复核翻上来的两道重复题因此漏网，是用户发现的。改判 → 重扫，无例外。

**9. 时间锚点是数据采集时点，不是今天。**
本项目锚点 2026-03-06（uid 前缀 `log_26_0306`）。拿核实当天的日期去翻案会制造假错误（票价/在售状态/版本号类题目全中招）。

**10. 不信任 judge 自报的结论，用脚本独立重算。**
judge 说「自校验全绿」不作数。必须有一个**不依赖 judge 输出的 step3、只用 step1+step2 重算**的校验脚本，逐题比对。模板见 `scripts/validate_batch.py`。判断题性质的例外（拒答豁免、安全题、n_wrong 无法确定）单独排除出机械比对并打印提示，不静默跳过。

## 目录与产物约定

```
<work>/
├── batches/batch_001.json ...      切好的批次，每批含题面 + 回答 + 原文题面
├── results/batch_001.json ...      judge 产出，顶层含 judge_model
├── tmp/                            临时文件，文件名必须带批次号
├── instructions.md                 发给每个 judge 子 agent 的唯一权威文档
├── validate_batch.py               独立重算校验
└── backfill_xlsx.py                幂等回填，--write 才落盘并自动备份
```

四条约定：

- **临时文件必须带批次号**（`tmp/batch_007_step1.json`）。多 agent 并发共享同一目录，`step1.json` 这种通用名会被同级 agent 覆盖，导致读到**别的批次的题**。读回自己的临时文件后，核对其中的 id 与批次文件一致。
- **审计轨迹与交付口径分离**。去重题在 `results/*.json` 里保持真实判定（`selected=是`），只在交付层写「否 + 重复query」，`review_note` 注明真实结论。不要回头篡改审计文件。
- **不直接改原始数据文件**。产出独立标注表，用唯一 id 关联回原表。
- **每次口径调整前整批备份**结果目录，可回溯对比。

## 开工前 checklist

1. judge 模型选定，确认不在候选名单里
2. 判定规则文档写完并冻结（一份，唯一权威；口径有变**改文档**，不要只在对话里口头改）
3. 校验脚本先于全量执行写好，用 pilot 批次跑通
4. pilot 校准：每个 domain / 每种题型抽 10 条实跑，据此修订规则再全量。本项目在 42 条 + 100 条两次 pilot 上共修订了 8 处规则，全量跑完才发现的问题只能重跑
5. 统计口径（分母、子集划分）在开跑前就写清楚

## 一个提醒

本 skill 里出现的具体枚举值（考察点标签表、rejection_type 九类、失败模式枚举）来自一次具体任务，是**实例不是规则**。换数据集要按新任务重新定义标签体系——但上面十条硬纪律和 `references/pitfalls.md` 是跨任务成立的。
