# Agent QC Standard Builder

把一批新数据和人工裁决，转化为能够被另一位标注员或检测算子稳定执行的质检标准。

本 skill 以**写新标准**为主、**审查现有标准**为辅。默认走 data-first 路径，不从维度名称、旧标签或现有算子命中理由直接生成标准。

## 核心闭环

```text
新数据
  → Agent 数据探查
  → 发现性抽样
  → 人工复判
  → 标准草案
  → 按标准回标
  → 独立样本验证
  → 标准冻结
```

标准草案不是终点。没有完成回标与独立验证，只能标记为 `DRAFT`，不能宣称标准已经验证。

## 两种工作模式

### A. 新标准模式（默认）

用户给出新数据、质检维度或模糊的问题描述，希望形成检测标准时使用。按完整闭环执行；如果用户已经完成某些阶段，先检查现有产物，再从最早缺失的阶段继续，不重复已完成且可信的工作。

### B. 标准审查模式（辅助）

用户明确要求审查、复核或改进已有标准时使用。读取 `references/review-checklist.md`，先报告问题，不在只读审查请求中直接改写文件。若审查发现必须回到数据才能裁决，转入新标准模式的对应阶段。

## 开始前先做什么

1. 确认用户要的是新标准、现有标准审查，还是从中间阶段继续。
2. 读取数据说明、schema、现有标签含义、已有算子输出和处置策略。把缺少的前置信息列为待确认项，不用常识偷偷补齐。
3. 建立一张**暂定维度卡**，只锁定探索边界，不提前写完整标准：

```yaml
core_question: 当前维度唯一要回答的问题
suspected_defect: 目前怀疑的缺陷是什么
training_harm: 为什么它可能伤害训练数据
in_scope: 当前探索纳入什么
out_of_scope: 明确不纳入什么
observable_evidence: 数据内能看到什么证据
adjacent_dimensions: 可能混入的相邻问题
```

`core_question` 是防止主题偏离的主锚点。它可以在人工复判前修订；开始写标准后，若要改变它，必须显式说明相当于改变检测维度，而不是普通措辞优化。

## 主流程

完整操作细则见 `references/data-first-workflow.md`。以下步骤不能无理由跳过。

### 1. Agent 数据探查

先描述数据，再解释数据：

- 还原真实 schema、字段嵌套、消息角色、索引含义和证据位置。
- 区分原始轨迹、已有标签、规则命中信息、人工备注和派生字段。
- 将已有标签视为弱信号，不视为 Ground Truth。
- 统计数据来源、任务类型、工具、轨迹长度、命中路径、重复轨迹和缺失字段。
- 对超大 JSONL 使用流式读取；先做小样本解析，再跑全量描述性统计。
- 将格式兼容、索引陷阱和解析限制写入技术说明，不写进缺陷定义。

这一阶段的产物是数据画像、字段地图和抽样建议，不是最终标准。

### 2. 发现性抽样，并提前封存独立验证集

把样本分成不同用途：

- **发现集**：覆盖现有算子命中、不同来源、不同结构、疑似正例、hard negatives、模糊案例和高风险形态，用来发现规则。
- **独立验证集**：在规则成形前按 ID 封存，标准制定期间不得查看其标签或内容。
- **未命中对照**：从现有算子未召回的数据中抽取，用来发现漏召；缺少这一组时，不报告 recall。
- **自然随机样本**：用于估计总体分布。定向样本只能用于发现问题，不能外推总体问题率。

同一轨迹的不同 turn 不得跨集合。优先按稳定的 trajectory ID 分组切分；没有稳定 ID 时，先建立可解释的去重键。

### 3. 为人工复判准备案例卡，并暂停

Agent 可以预分析和提出候选解释，但不能把自己的判断冒充为人工裁决。每个案例卡至少包含：

```yaml
case_id:
raw_locator:
candidate_evidence:
legacy_label:
legacy_reason:
agent_hypothesis:
alternative_explanation:
adjacent_dimension_risk:
human_decision: pending
human_reason: pending
```

向用户交付可复判的案例卡后暂停，等待人工决定。允许人工使用 `DEFECT / CLEAN / UNCERTAIN / OUT_OF_SCOPE` 或项目自己的映射；不要强迫证据不足的案例进入二分类。

人工发现的其他严重问题进入 `adjacent_issue_log`，不能因为“也很重要”就并入当前标准。

### 4. 从人工裁决归纳标准草案

收到人工复判后：

1. 按**因果机制**聚类理由，不按关键词或表面字符串聚类。
2. 选择最简单适用的算子原型；读取 `references/operator-archetypes.md`。
3. 用 `references/standard-template.md` 起草标准。
4. 把稳定规则、批次观察、技术实现限制和待确认事项分开。
5. 每加入一条规则，都执行主题三问：
   - 它是否直接改变 `core_question` 的答案？
   - 它是否有数据内可核验的证据？
   - 它是否更应属于相邻维度？

第一个或第二个答案为否时，不进入缺陷规则；第三个答案为是时，转出到相邻维度。

### 5. 按标准回标

用标准草案从头重判完整发现集和人工复判集。不能只复查原先的正例，也不能逐案例临时加补丁以追平人工结论。

输出至少包括：

- 与人工裁决一致；
- 标准推翻人工旧判断；
- 规则缺口；
- 证据不足；
- 边界重叠；
- 仍依赖临场解释。

若标准需要频繁依靠案例特例才能复现判断，回到第 4 步重写一般规则。重大翻案由人工确认后再进入验证。

### 6. 独立样本验证

标准冻结前必须使用此前封存的独立验证集：

- **标准可执行性验证**：由未参与规则归纳的人依据冻结 draft 独立判定；若只有同一位复判者，则至少隐藏发现集旧结论、间隔后盲判，并把独立性不足写入局限。检查的是标准能否被他人稳定理解和复现。
- **算子实现验证**：只有实现已经存在时才做。将算子输出与验证集上的人工裁决比较，检查实现是否忠实执行标准。不能拿算子自己的输出给自己当 Ground Truth。
- 不因验证结果不理想而逐例修改标准；先归纳系统性失败，再整体修订，并更换或重新封存下一轮验证集。
- 同时报 coverage、abstain、invalid 和分类结果；`UNCERTAIN / N_A` 不得并入 PASS 或 FAIL。
- precision 只对算子召回样本有意义；没有未命中对照或完整参照时，不宣称 recall。
- 对可能存在方向性偏差的来源、语种、schema 版本、工具或任务类型分桶报告。
- 小样本只能报告观察结果和置信限制，不伪造稳定百分比。

若独立验证失败，回到标准草案阶段迭代。若用户选择停止，明确交付状态是 `DRAFT` 或 `VALIDATION_FAILED`。

### 7. 冻结标准与拆分产物

冻结时记录版本、日期、适用数据形态、验证集来源、待确认项和下一次校准条件。至少分开维护：

1. **检测标准**：稳定定义、判定链、边界和证据要求。
2. **批次分析**：当前数据的数量、分布、案例和观察。
3. **技术实现说明**：schema、解析、索引、归一化和工程限制。
4. **校准与验证报告**：回标变化、人工分歧、独立验证表现和局限。

不要把批次比例、临时阈值、解析路径或未确认观察写成永久标准。

## 选择判定方法

不要让一个复杂方法覆盖全部工具维度。先选原型，再写判定链：

| 原型 | 典型问题 | 首选方法 |
|---|---|---|
| 结构／Schema 校验 | 工具名不存在、参数缺必填项 | 直接规则或 schema validator |
| 局部一致性 | thought 与 tool call 冲突 | 两侧规范化为契约后比较 |
| 状态转移 | 报错后假装成功、缺口未恢复 | 前态 → 事件 → 后续行为 |
| 轨迹模式 | 重复调用、循环、无进展 | 有界窗口、阈值和合法例外 |
| 声明—证据溯源 | 回复声称测试已通过 | 从声明回溯轨迹证据 |
| 信息变换与依赖 | 摘要失真、压缩后无依据使用 | 变换忠实度与下游依赖分开判 |

详细选择条件和每类必需章节见 `references/operator-archetypes.md`。

## 判定单元的角色

判定单元不是标准的叙事主轴。仅在它影响抽样、证据范围、处置或统计时展开：

```yaml
sampling_unit: 抽样时抽取什么
evidence_unit: 一次判断需要读取多大范围
decision_unit: 一次结论针对什么对象
disposition_unit: mask、修复或删除作用于什么对象
aggregation_unit: 指标最终按什么聚合
```

若这些单位相同，一句话说明即可；若不同，分别定义并使用不同分母，不能混算。

## 证据与结论纪律

始终保持下面的方向：

```text
原始证据 → 可复算的派生事实 → 缺陷结论 → 根因归属 → 严重度 → 处置
```

后一层不能反向定义前一层：

- 算子 trigger 不是缺陷证据。
- 建议 mask 不代表缺陷已经成立。
- 实际动作更合理不能改写模型此前明确表达的计划。
- 当前步骤之后出现的信息不能倒过来给当前步骤提供依据。
- “没有发现”只有在检索范围有界且被完整检查时才是有效证据。
- 规则能确定性完成时不用 LLM judge；需要 judge 时保留弃权路径和原文证据。

判错至少给出：原始定位、被检内容、对照证据、命中规则、直接冲突，以及为什么不属于关键 hard negative 或相邻维度。

## 审查现有标准

审查时读取 `references/review-checklist.md`，重点检查：

- 是否有唯一且稳定的 `core_question`；
- 规则是否逐渐收编相邻维度；
- 是否把观察、trigger、标签或处置误作缺陷定义；
- 否定断言是否建立在完整且有界的阅读范围上；
- 是否保留证据不足、不可适用和数据无效状态；
- 标准是否经历回标和独立验证；
- 批次结论是否污染了通用规则。

默认先给审查报告和修改建议；只有用户要求修改时才改写标准。

## 完成条件

只有同时满足以下条件，才把新标准标为 `FROZEN`：

- 人工复判已完成，并保留裁决依据；
- 标准能够回放到发现集，重大翻案已人工确认；
- 独立验证集此前未参与规则制定；
- 独立验证由独立复判者执行，或已明确记录较弱的盲判替代方案；
- 独立验证结果、弃权和局限已记录；
- 标准、批次观察、技术说明和验证报告已分离；
- 待确认项不影响核心判定链，或已明确阻塞发布。

任何一项未满足，都诚实标记为 `DRAFT`、`CALIBRATING` 或 `VALIDATION_FAILED`。
