# Data-first 质检标准生成闭环

这份参考文件把主 skill 的七个阶段展开成可执行动作。它适用于新的 Agent 轨迹数据，不假设已有标签正确，也不假设现有算子的召回范围完整。

## 1. 阶段总览

| 阶段 | 核心问题 | 主要产物 | Gate |
|---|---|---|---|
| 数据探查 | 数据实际长什么样、证据在哪里 | 数据画像、字段地图、技术风险 | 能稳定定位原始证据 |
| 发现性抽样 | 哪些样本能帮助发现边界 | 发现集、封存验证集、未命中对照 | 各集合按轨迹隔离 |
| 人工复判 | 人如何解释证据与缺陷 | 案例卡、裁决、分歧和相邻问题 | 人工确认完成 |
| 标准草案 | 哪个最小规则能解释裁决 | Draft 标准 | 核心问题和边界稳定 |
| 按标准回标 | 规则能否复现人工判断 | 回标对照、规则缺口 | 重大翻案已裁决 |
| 独立验证 | 规则能否迁移到未见数据 | 验证报告 | 达到项目验收口径 |
| 冻结 | 交付是否可执行、可追溯 | Frozen 标准及配套文档 | 待确认项不阻断判定 |

## 2. 数据探查

### 2.1 先建立来源分层

将字段分成四组，避免把派生结论误当原始事实：

| 层 | 例子 | 用法 |
|---|---|---|
| 原始输入 | user、system、tool schema、环境状态 | 任务与约束证据 |
| 模型输出 | thought、content、tool_calls | 主要被检对象 |
| 环境反馈 | tool result、verifier、error code | 执行和状态证据 |
| 派生信息 | 旧标签、reason code、规则命中说明 | 抽样线索，不是 Ground Truth |

### 2.2 最小探查清单

- 顶层 schema 和版本字段。
- assistant 消息、candidate、labels、tool result 的嵌套方式。
- ID 是否唯一，turn index 是否跨字段复用。
- tool call 是否存在多种序列化形态。
- 同一轨迹是否被多个规则或多个 turn 重复命中。
- 数据来源、任务类型、语言、工具和轨迹长度分布。
- 缺失、截断、无效 JSON、空字段和超大行。
- 旧标签是谁产生的、采用什么标准、是否经过人工裁决。

先抽 5–20 条验证解析逻辑，再做全量描述性统计。全量读取大文件时采用流式处理，并把无法解析的记录单列为数据问题，不静默丢弃。

### 2.3 探查输出

数据画像至少回答：

1. 数据共有多少记录、多少独立轨迹。
2. 当前维度可能涉及哪些字段。
3. 证据如何从派生记录回到原始轨迹。
4. 哪些结构差异会影响判定或实现。
5. 哪些数字是事实统计，哪些只是初步假设。

## 3. 抽样设计

### 3.1 四种用途不要混用

| 集合 | 选取方式 | 能回答什么 | 不能回答什么 |
|---|---|---|---|
| 发现集 | 定向、分层、极端值、疑似边界 | 缺陷有哪些形态、边界在哪里 | 总体发生率 |
| 回标集 | 发现集 + 人工裁决集 | 标准是否能复现既有判断 | 对未见数据的迁移能力 |
| 独立验证集 | 规则形成前封存，优先随机或分层随机 | 标准在未见数据上的表现 | 新规则的训练材料 |
| 未命中对照 | 从现有算子未命中池抽样 | 漏召形态、recall 线索 | 单独估计 precision |

### 3.2 发现集的覆盖轴

根据数据选择有意义的轴，不机械追求每轴齐全：

- 数据来源或生成方式；
- task/domain；
- schema_version；
- tool 或调用形态；
- 轨迹长度、调用数量和文件大小；
- 现有 reason code；
- 旧标签正反例；
- 多语言；
- 疑似 hard negative；
- 高后果操作；
- 空调用、多调用、失败调用等结构形态。

### 3.3 防止集合泄漏

- 按 trajectory ID，而不是按命中记录 ID 切分。
- 同源模板或近重复轨迹尽量进入同一集合。
- 验证集只记录封存 ID 与抽样策略；标准制定阶段不读取其内容。
- 若样本量太小无法真正独立验证，使用 leave-one-source-out 或 leave-one-pattern-out，并明确这只是较弱验证。

## 4. 人工复判

### 4.1 案例卡

案例卡要让人能看到足够证据，又不被旧标签牵引。推荐先展示原始证据，再折叠展示旧标签与 Agent 假设。

```yaml
case_id:
trajectory_id:
raw_locator:
source_bucket:
core_question:
inspected_text:
comparison_evidence:
legacy_label:
legacy_reason:
agent_hypothesis:
hard_negative_candidate:
adjacent_dimension_candidate:
human_decision: pending
human_reason: pending
human_evidence: pending
```

### 4.2 人工裁决纪律

- 先答 `core_question`，再讨论严重度和处置。
- 旧标签和现有算子结果是参考，不是答案。
- 无法获得关键证据时选择 `UNCERTAIN`，而不是凭经验补齐。
- 问题属于其他维度时选择 `OUT_OF_SCOPE`，并记录转出方向。
- 人工修改结论时保留旧值和修改原因，不覆盖审计轨迹。
- 有多位复判者时先独立判断，再讨论分歧；讨论结果回写规则依据。

### 4.3 从人工裁决中提取什么

不要只统计标签。重点提取：

- 人工反复使用的证据类型；
- 造成分歧的语义边界；
- 经常被误判的 hard negatives；
- 哪些案例必须借助数据外知识；
- 哪些问题其实属于相邻维度；
- 不同处置是否隐含了不同缺陷定义。

## 5. 从案例归纳标准

### 5.1 先归因，再命名

将案例按“为什么构成或不构成缺陷”聚类，而不是按共同关键词聚类。一个有效规则应能同时解释正例和最接近的反例。

### 5.2 三层分离

```text
稳定标准：跨批次应成立的定义、逻辑、边界和证据要求
批次观察：当前数据的数量、集中形态、典型案例和风险
实现说明：字段路径、解析兼容、索引、映射和性能约束
```

三层可以互相引用，但不能互相替代。

### 5.3 规则进入标准的条件

一条候选规则必须同时满足：

1. 回答当前 `core_question`；
2. 能指出可访问的原始证据；
3. 至少有一个正例和一个接近的反例支撑，或能由确定性契约直接推出；
4. 不依赖当前批次的文件名、工具名或偶然比例；
5. 能说明证据不足时如何退出。

## 6. 按标准回标

### 6.1 回标方式

- 使用冻结的 draft 版本，不边判边改。
- 尽量隐藏人工旧结论，降低确认偏差。
- 输出标准结论、证据、命中规则和弃权原因。
- 完成整轮后统一比较，不在中途为单条案例添加例外。

### 6.2 回标差异表

| 差异类型 | 含义 | 下一步 |
|---|---|---|
| `MATCH` | 标准复现人工裁决 | 保留 |
| `HUMAN_OVERTURNED` | 标准显示旧人工判断不符合已冻结规则 | 人工复核是否接受翻案 |
| `RULE_GAP` | 人工理由合理，但标准无规则覆盖 | 抽象一般规则后重跑全批 |
| `EVIDENCE_GAP` | 当前数据不足以支持原判断 | 改为弃权或补数据 |
| `SCOPE_CONFLICT` | 案例应属于相邻维度 | 转出，不扩张当前标准 |
| `CASE_PATCH_REQUIRED` | 只能靠给单条样本打补丁才能对齐 | 不接受；重新审视规则或裁决 |

### 6.3 回标验收不只看一致率

高一致率可能只是标准照抄案例。还要检查：

- 差异是否集中在同一边界；
- 弃权是否集中在某种语言、来源或 schema；
- hard negatives 是否稳定排除；
- 规则是否需要知道具体 case ID 才能工作；
- 多位标注者是否能独立复现。

## 7. 独立验证

### 7.1 打开验证集的时机

只有当 draft 的核心问题、结果状态、判定链和边界全部冻结，且回标中的重大分歧已经解决，才能打开验证集。

### 7.2 验证对象

独立验证分两层，不能让标准或算子自证正确：

| 层 | 被验证对象 | 参照 | 主要结果 |
|---|---|---|---|
| 标准可执行性 | 标准文本 | 未参与规则归纳的人使用冻结 draft 的独立判断 | 一致性、弃权、歧义与边界失败 |
| 算子实现 | 代码或 judge 实现 | 验证集上的人工裁决 | precision、recall、coverage 与分桶误差 |

如果当前只有标准、没有算子，只做第一层即可。如果没有第二位复判者，至少让原复判者在不知道发现集旧结论和 Agent 预测的情况下盲判，并明确这不是完全独立验证。

### 7.3 指标纪律

根据数据条件选择指标，不强求齐全：

```text
coverage      = 可判样本 / 全部有效样本
abstain_rate  = 弃权样本 / 全部有效样本
invalid_rate  = 数据无效样本 / 全部样本
precision     = 真缺陷 / 算子召回
recall        = 真缺陷中的召回数 / 全部真缺陷
```

- 没有抽取未命中样本或建立完整参照时，不报告 recall。
- 定向配额样本不能估计总体 prevalence。
- 不同判定单位使用不同分母，不能把“轨迹数、step 数、问题行数”相加。
- 若弃权率高，只报告 precision 会掩盖覆盖问题；二者必须并列。
- 对方向性风险按来源、语种、schema、工具或任务类型分桶。

标准文本的可执行性验证不应只看最终标签一致率，还要记录：规则引用是否一致、弃权原因是否一致、同一 hard negative 是否稳定排除，以及是否频繁需要文档外解释。

### 7.4 验证失败后的处理

1. 不为验证集中的单条样本增加特例。
2. 归纳失败是否来自定义、证据、边界、解析或分布变化。
3. 若修改了标准，将当前验证集转为已见数据；下一轮需使用新的封存集。
4. 保留各版本标准和改动原因，避免事后覆盖。

## 8. 冻结与再校准

标准冻结记录至少包括：

```yaml
version:
status: FROZEN
core_question:
applicable_schema_versions:
discovery_set:
validation_set:
validation_reviewer:
validation_mode: independent_reviewer / blinded_same_reviewer
validation_summary:
known_limits:
open_questions:
last_calibrated_at:
recalibration_triggers:
```

重新校准的触发条件包括：数据源或生成模型变化、schema 升级、工具行为变化、命中率异常漂移、弃权集中、相邻维度重定义，或下游处置策略发生变化。
