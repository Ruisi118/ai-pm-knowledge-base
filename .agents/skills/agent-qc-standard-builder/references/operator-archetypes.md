# Agent 质检算子原型

先选择最简单、最贴近证据结构的原型，再写标准。一个维度可以由多个原型组成，但每个子问题应明确属于哪一种；不要把多种逻辑揉成一条不可解释的判定链。

## 快速选择

依次回答：

1. 只靠 schema、类型、集合成员关系或确定性程序就能判断吗？能则选**结构／Schema 校验**。
2. 是否在比较同一局部范围内的两个表达或动作？是则选**局部一致性**。
3. 是否必须知道某个事件前后的状态变化？是则选**状态转移**。
4. 是否依赖一段序列中的重复、循环、停滞或阈值？是则选**轨迹模式**。
5. 是否从模型的一条声明回溯有没有执行证据？是则选**声明—证据溯源**。
6. 是否检查内容从 A 变成 B 后的忠实度，或 B 被下游如何使用？是则选**信息变换与依赖**。

如果多个答案为“是”，先拆成子问题。只有共享同一缺陷定义、证据结构和处置方向的子问题才合并。

## 1. 结构／Schema 校验

### 适用

- 工具名是否存在于声明集合；
- arguments 是否可解析；
- required 字段是否存在；
- 类型、枚举和结构是否符合 schema；
- tool call 与 result 的结构数量是否匹配。

### 判定骨架

```text
声明契约／schema
  → 规范化实际值
  → 确定性 validator
  → PASS / FAIL / N_A / INVALID
```

### 标准必须写清

- schema 版本和适用数据类型；
- 条件必填与任务类型豁免；
- 可安全修复的格式问题与真正缺陷的边界；
- 前置 schema 缺失时返回 `N_A`，而不是 FAIL；
- framework 内置工具、字段别名和透传参数等白名单如何维护。

### 不要做

- 不用 LLM judge 替代 JSON/schema validator。
- 不把 schema 本身错误归咎于数据。
- 不把可归一化差异直接升级成删除理由。

## 2. 局部一致性

### 适用

- thought 与同一 turn 的 tool calls；
- 调用承诺与实际调用；
- 局部声明的目标、参数或操作效果与实际动作。

### 判定骨架

```text
表达 A → Expected Contract
表达 B → Actual Contract
           ↓
      逐字段比较
```

### 标准必须写清

- 比较范围必须局部且同源，例如同一 assistant turn；
- 哪些表述属于当前、未来、过去、条件、备选或已撤销；
- 名词在文本中的语义角色：操作对象、搜索容器、要找的内容、原因线索或背景；
- 工具、目标、参数、操作效果和调用集合的比较优先级；
- 只比较明确约束的字段；宽泛承诺按能力类比较。

### 不要做

- 不根据实际动作反推表达 A “真正想做什么”。
- 不用“实际动作更合理”消解直接冲突。
- 不把执行成功、任务完成度或 schema 合法性混进当前维度。

## 3. 状态转移

### 适用

- 工具报错后是否正确重试、降级或说明；
- 信息缺口出现后是否承认或恢复；
- 授权状态、任务状态或资源状态变化后的行为。

### 判定骨架

```text
前态 S0
  → 事件 E
  → 可观察的新状态 S1
  → 后续动作 A
  → A 是否与 S1 相容
```

### 标准必须写清

- 状态来自什么原始证据；
- 事件何时生效；
- 回看和前看窗口的边界；
- retry、fallback、acknowledgement 和 recovery 的合法形态；
- 状态未知或反馈延迟时如何弃权；
- 哪些正确恢复行为应单列为高价值正例。

### 不要做

- 不凭 error、failed 等关键词直接判失败，优先使用结构化状态。
- 不把“事件存在”当成“后续处理错误”。
- 不用事件之后才获得的信息为更早步骤补证。

## 4. 轨迹模式

### 适用

- 重复调用；
- 循环、停滞、无进展；
- 步数、重试次数或调用密度异常；
- 一段窗口内的行为序列。

### 判定骨架

```text
轨迹事件序列
  → 规范化事件
  → 在有界窗口内计算模式／度量
  → 排除合法循环
  → 阈值判定
```

### 标准必须写清

- 窗口起止和事件规范化方式；
- 阈值对应的原始 value；
- polling、分页、重试、并行或逐块处理等 hard negatives；
- 阈值是否按任务类型、难度或工具分桶；
- 阈值的校准时间和数据来源。

### 不要做

- 不使用跨任务的单一全局阈值。
- 不只存 flag；保留重复次数、步区间和归一化参数等原始度量。
- 不把正确重试当作坏数据。

## 5. 声明—证据溯源

### 适用

- final answer 声称已运行测试、修改文件、发送消息或完成任务；
- 模型声称某工具结果支持结论；
- 需要验证一个输出声明是否在轨迹中有落点。

### 判定骨架

```text
提取可验证声明
  → 定义其最低证据要求
  → 在完整且有界的轨迹范围内回溯
  → VERIFIED / CONTRADICTED / UNSUPPORTED / N_A
```

### 标准必须写清

- 哪些是可验证声明，哪些只是建议、意图或主观评价；
- 不同声明需要什么证据；
- 检索范围为何完整且有界；
- “没有找到证据”和“证据证明相反”的区别；
- 工具调用本身与成功结果的区别。

### 不要做

- 不把 tool call 存在等同于任务成功。
- 不在只读了部分长轨迹时作“全程没有”的否定断言。
- 不把回答质量、文风或用户满意度混入证据存在性。

## 6. 信息变换与依赖

### 适用

- 上下文压缩、摘要、重写或结构化转换是否忠实；
- 变换后是否保留继续任务所需的依赖；
- 下游步骤是否使用了已丢失且未重新获取的信息。

### 判定骨架

拆成两个子问题：

```text
A. 变换忠实度：Source → Transformation → Product
B. 下游依赖：Available Context → Dependency → Usage
```

两者可能具有不同证据范围、判定单位和处置方式，不要合并为单一命中率。

### 标准必须写清

- 变换事件是否真的发生，还是界面折叠、首次截断或导出缺失；
- 原文和变换结果是否同时可见；
- 允许删除哪些细节，必须保留哪些状态或约束；
- 下游首次使用依赖的时间点；
- 重新获取是否发生在使用之前，返回是否包含足够内容；
- 无法访问变换前原文时，哪些结论必须弃权。

### 不要做

- 不把“摘要比原文短”判为缺陷。
- 不把变换产物失真、下游无依据使用和完整 candidate 错误混成一个结论。
- 不看到工具调用就假定依赖已恢复；还要检查时序和返回内容。

## 多原型标准的拆分规则

如果一个维度同时需要多个原型，逐项确认：

| 问题 | 若答案不同 |
|---|---|
| 缺陷命题是否相同 | 拆成相邻维度 |
| 证据能否在同一范围内取得 | 拆成不同子问 |
| 判定结论是否同一套 | 分别输出 |
| 处置范围是否相同 | 分别记录，不合并指标 |
| 成熟度是否相同 | 分开标记 draft / validated |

多原型不是问题；不说明它们为何放在一起，才会造成标准主题漂移。
