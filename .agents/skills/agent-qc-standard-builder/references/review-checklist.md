# 现有质检标准审查清单

审查的目标是判断一份标准能否稳定回答它声称的问题。默认先出审查报告，不直接改写原文。

## 1. 审查输出格式

```markdown
# <标准名称> 审查报告

## 结论
PASS / REVISION_REQUIRED / BLOCKED_BY_MISSING_EVIDENCE

## Core question 复原
<从标准正文还原的一句话>

## P0 问题
<会改变缺陷定义、造成系统性误判或使结果不可复现的问题>

## P1 问题
<边界、证据、输出或验证不足>

## 可保留资产
<定义、案例、判定步骤、hard negatives>

## 建议修改顺序
<先定义，再判据，再输出与指标>

## 需要回到数据确认的问题
<不能只靠改文档解决的事项>
```

## 2. 主题锚定

- [ ] 能否用一句话写出唯一的 `core_question`？
- [ ] 标题、检测目标、判定链和命中类型是否在回答同一个问题？
- [ ] 是否因为某个问题严重，就被顺手并入当前维度？
- [ ] 是否混入 schema、执行结果、任务完成度、回答质量等相邻维度？
- [ ] 标准是否提供明确的转出路径，而不是只写“不检测”？

### 逐规则主题测试

对每条规则问：

1. 删除这条规则会改变 `core_question` 的答案吗？
2. 这条规则直接使用什么原始证据？
3. 它是在定义缺陷，还是在描述 trigger、根因、严重度或处置？
4. 它是否更适合放进相邻标准？

无法通过前两问者不应作为缺陷判据。

## 3. 定性与因果方向

- [ ] 缺陷命题是否说明“什么条件下，什么行为为何有害”？
- [ ] 前置事实是否与缺陷结论分开？
- [ ] 是否存在“因为建议 mask，所以一定有缺陷”的逆向定义？
- [ ] 是否把 operator hit、关键词、旧标签或人工备注当成原始证据？
- [ ] 根因、严重度和处置是否在判定完成之后才出现？
- [ ] 实际结果更合理、最终任务完成等后验信息是否被用于改判局部一致性？

## 4. 证据可达性

- [ ] 标准是否说明允许读取哪些字段和时间范围？
- [ ] 当前步骤之后的结果是否被错误用于当前步骤？
- [ ] “没有出现”“从未调用”等否定断言是否建立在完整、有界的检索范围上？
- [ ] 原文不可见时是否有 `UNCERTAIN` 或 `NOT_VERIFIABLE` 路径？
- [ ] 名称、ID、路径和别名的等价是否有可确认映射？
- [ ] 工具调用与工具成功返回是否被区分？

## 5. 判定链与算子原型

- [ ] 是否选择了与证据结构一致的原型？
- [ ] 确定性规则能完成的部分是否避免使用 LLM judge？
- [ ] 多个子问题是否拥有不同的证据范围、结果或处置？若是，是否拆开？
- [ ] 每一步是否有输入、输出、停止条件和弃权条件？
- [ ] primary type 的选择是否确定，而非自由文本？
- [ ] 是否存在只有具体 case ID 才能解释的例外补丁？

## 6. Hard negatives 与过召

- [ ] 每个主要命中类型是否至少有一个最接近的反例？
- [ ] 正确重试、恢复、fallback、分页、轮询和多步执行是否被保护？
- [ ] 背景提及、原因线索、搜索内容和操作对象是否区分？
- [ ] 未来步骤、条件动作、备选方案和已撤销计划是否排除？
- [ ] 过召是否可能集中在长轨迹、多语言、特定 schema 或工具？
- [ ] 对方向性过召是否要求分桶，而不是只报总体均值？

## 7. 结果状态与输出

- [ ] PASS 是否只表示“已检查且没有缺陷”？
- [ ] `UNCERTAIN / NOT_APPLICABLE / INVALID` 是否独立？
- [ ] 判错是否要求原始定位、被检证据、对照证据、规则和排除反驳？
- [ ] 输出是否保留原始 value，便于阈值或规则调整？
- [ ] 相邻维度是否有机器可读的 route_to？

## 8. 单位、处置与指标

- [ ] sampling、evidence、decision、disposition、aggregation unit 是否真的需要区分？
- [ ] 如果单位不同，是否分别声明并使用不同分母？
- [ ] 是否混算轨迹数、step 数、call 数和问题行数？
- [ ] mask、filter、repair 和只标记是否与缺陷严重度相匹配？
- [ ] 定向样本是否被错误用于总体发生率？
- [ ] 只有召回样本时是否错误声称 recall？
- [ ] defect rate 是否与 coverage、abstain 和 invalid 并列？

## 9. Data-first 闭环

- [ ] 标准是否来自真实数据探查和人工复判，而不只是概念推演？
- [ ] 人工裁决是否保留理由和证据？
- [ ] 是否用 draft 标准重新回标发现集？
- [ ] 重大翻案是否经过人工确认？
- [ ] 是否存在规则制定前封存的独立验证集？
- [ ] 是否由未参与规则归纳的人独立执行验证；若做不到，是否记录了盲判替代方案的局限？
- [ ] 若已有算子，是否用人工裁决验证实现，而不是让算子自证？
- [ ] 验证集一旦用于修改规则，是否退出“独立”身份？
- [ ] 标准状态是否如实标为 DRAFT、CALIBRATING 或 FROZEN？

## 10. 文档分层

- [ ] 稳定规则是否留在检测标准？
- [ ] 批次数量、比例和案例是否放在批次分析？
- [ ] 字段路径、解析兼容和性能是否放在技术实现说明？
- [ ] 回标、验证、分歧和局限是否放在校准报告？
- [ ] 待工程确认的事实是否被误写成已成立规则？

## 11. 审查结论规则

### `PASS`

核心问题稳定，证据链可执行，关键边界有 hard negatives，结果状态完整，并已完成回标与独立验证。

### `REVISION_REQUIRED`

方向正确但存在可修订问题，例如边界重叠、证据字段不足、输出不完整、单位混算或尚未完成验证。

### `BLOCKED_BY_MISSING_EVIDENCE`

关键原文、schema、工具结果、时间顺序或人工裁决不可获得，仅靠文字改写无法形成可靠标准。

审查结论评价的是标准成熟度，不等同于该检测维度是否值得建设。
