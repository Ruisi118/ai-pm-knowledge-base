# 两类质检任务提炼出的可迁移经验

这些案例用于解释方法来源，不是可直接复制的业务标准。遇到新维度时，应根据新数据重新定义缺陷、证据和标签。

## 案例一：上下文压缩

### 初始表象

数据中出现 summary、内容占位、工具输出不可见、后续步骤继续执行等现象，很容易统称为“上下文压缩问题”。

### 实际需要拆开的子问题

1. 压缩事件是否真的发生；
2. 压缩范围是否遗漏了不应整体丢失的类别；
3. 压缩产物写出来的事实是否忠实；
4. 后续步骤是否使用了已经丢失且未重新获得的信息；
5. candidate 的 reasoning、content、tool calls 是否还存在其他独立错误。

这些问题的原始证据、可判性和处置位置不同。如果把它们合并成一个“压缩有问题”，召回、质量与训练处置会互相污染。

### 可迁移经验

- 先确认事件来源。界面折叠、首次截断、脱敏或导出缺失不自动等于压缩。
- 信息变换类问题至少分为“产物忠实度”和“下游依赖”两条链。
- 内容被删除不天然是缺陷；摘要的职责本来就包括删减。
- 重新调用工具不等于依赖已恢复；要同时检查调用时序和返回内容。
- 原文不在数据内时，不能判摘要忠实度，只能判断证据是否足够或下游行为是否越界。
- 多个单位只有在其证据和处置不同的时候才需要重点展开。

### 不能泛化的部分

- 固定 summary 小节、Note 格式、candidate 结构和当前批次的路径字段；
- 特定问题数量和命中比例；
- 某一批数据的 mask 策略。

## 案例二：思考—工具调用不一致

### 初始表象

thought 里出现的工具名、文件名或业务对象与实际 tool calls 不同，看起来可以直接做字符串比较。

### 真正的判定任务

先从 thought 中提取最终仍成立、明确指向本轮执行的承诺，再与同一 assistant turn 的实际调用比较。

以下名字虽然出现在 thought 中，但不一定是当前调用约束：

- 已完成的历史动作；
- 之后才执行的未来步骤；
- 条件动作；
- 被后文撤销的候选方案；
- 允许任选其一的备选；
- 解释原因的线索；
- 搜索中要寻找的内容，而非搜索容器。

### 可迁移经验

- 局部一致性问题先把两侧编译成结构化 contract，再逐字段比较。
- 文本中“出现了同一个词”不等于承担相同语义角色。
- 只比较计划明确约束的工具、目标和参数，不补充模型没有承诺的要求。
- 实际动作即使更聪明或更正确，也不能反向改写明确计划。
- 当前步骤、并列动作、备选动作和未来步骤必须分开。
- 旧 reason code 和初始标签适合召回案例，不适合作为判错证据。

### 不能泛化的部分

- 某一批数据中的工具名、文件路径和类型分布；
- 特定 primary type 枚举；
- 默认认为 tool_calls 数组顺序等于模型原始执行顺序。

## 两个案例共同证明了什么

### 1. Trigger、证据和结论必须分开

```text
算子为什么把样本捞出来
≠ 原始数据里发生了什么
≠ 这个现象是否构成缺陷
≠ 命中后应该怎样处置
```

### 2. 标准要从案例中归纳，但不能被案例绑架

案例负责揭示边界，标准负责给出一般规则。将 case ID、具体文件名或批次比例写进规则，通常意味着过拟合。

### 3. 证据不足不是干净

没有计划可比、原文不可见、对象映射不明或数据损坏时，应输出不适用、弃权或无效，而不是记成 PASS。

### 4. 否定断言需要有界范围

“从未出现”“没有重新读取”“摘要完全没提到”等判断，只有在判定者完整检查了明确边界内的内容时才成立。长轨迹只读开头便作全局否定，会产生方向性过召。

### 5. 正确行为也值得单独标记

识别缺口并恢复、错误后正确重试、清楚限定结论范围等，不应只是“没有缺陷”；它们是高价值训练正例，需要可被采样和下游消费。

### 6. 标准、分析和实现必须分层

- 标准回答“什么算缺陷”；
- 批次分析回答“这批数据发生了什么”；
- 技术说明回答“如何从字段中取到证据”；
- 校准报告回答“规则能否复现并迁移”。

混在一起时，标准会被当前批次的数据结构和偶然分布绑死。

## 从案例走向新标准时的检查

面对一个新的工具调用维度，先问：

1. 它更像确定性契约、局部一致性、状态转移、轨迹模式、声明溯源，还是信息变换？
2. 当前数据能支持的是事实判断，还是只能支持风险召回？
3. 最接近的合法行为是什么？
4. 当前人工裁决中是否混用了多个隐性问题？
5. draft 标准能否在隐藏旧标签的情况下复现这些裁决？
6. 在未见样本上失败时，失败来自规则、证据、解析还是分布变化？

这六问比复制任何一个既有标准的章节结构更可靠。
