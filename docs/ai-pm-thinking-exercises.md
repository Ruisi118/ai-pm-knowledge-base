# AI PM Thinking 训练手册

> 基于 AI 产品面试真题，提炼通用思维框架 + 多产品对比分析

---

## 前言

### 这份手册的目的

通过 12 道高质量面试题，训练**可迁移的 AI PM 思维能力**。每道题不仅给出分析思路，更重要的是提炼出**可复用的分析框架**——这些框架适用于任何 AI 产品。回答示例覆盖国内外 11 个主流产品，保持中性客观视角。

### AI PM 思维的三层模型

| 层级 | 关注点 | 典型问题 |
|------|--------|----------|
| **应用层** | 功能、交互、用户体验 | "这个功能好不好用？" |
| **评估层** | 指标、评测、质量定义 | "怎么衡量'好'？" |
| **数据闭环层** | 训练数据、奖励信号、模型迭代 | "怎么让它持续变好？" |

> 高水平的回答应该展示你在**评估层和数据闭环层**的思考，而非只停留在应用层。

### 每道题的结构

- **考察维度** — 这道题在评估什么能力
- **Why** — 为什么问这个问题
- 🧠 **通用思维框架** — 可迁移到其他产品/场景的分析模型
- **回答示例** — 多产品对比的具体分析
- **延伸思考** — 更深层的洞察与延展方向

## Part 1: 产品与竞品分析

### Q1: 千问、ChatGPT、豆包、Kimi、DeepSeek 这类 AI 对话产品的差异？千问最应该补齐的短板是什么？

**考察维度：** 竞品认知深度 + 分析框架 + 独立判断力

**Why：** 这道题训练的核心能力是**结构化竞品分析**——能否跳出功能列表，用统一框架横向切产品差异，并对每个产品给出客观的优劣势判断。AI 对话市场变化极快，PM 需要持续追踪并形成自己的分析体系。

#### 🧠 通用思维框架：维度矩阵竞品分析法

**核心原则：不要逐产品列功能，而是用统一维度横向切。**

适用于任何 AI 产品竞品分析的六维矩阵：

| 维度 | 问什么 |
|------|--------|
| **核心身份定位** | 这个产品用一句话怎么描述自己？它站在谁那一边？ |
| **交互范式** | 用户与产品交互的主要方式是什么？（纯对话/带工具/多模态） |
| **模型能力边界** | 哪类任务做得特别好？哪类明显不行？ |
| **生态与分发** | 用户从哪来？产品嵌入了什么生态？ |
| **记忆与个性化** | 产品是否记住用户？如何做个性化？ |
| **多模态能力** | 支持哪些模态的输入/输出？ |

**自检问题（taste 框架）：** "拿掉模型光环，这个产品还剩什么独特判断？"——如果换一个同等能力的模型，产品体验会变化多大？变化越小，说明产品层的 taste 越弱。

**行业级洞察：**

1. **规模 ≠ 心智**：豆包和千问的 MAU 都过亿，但很大程度靠生态分发和补贴拉动。真正的产品心智（用户主动选择）方面，ChatGPT、DeepSeek、Kimi 更强
2. **独立 App MAU ≠ AI 渗透率**：百度将 AI 能力嵌入搜索/地图/网盘，Gemini 嵌入 Google 全家桶——这些产品的 AI 实际触达用户远大于独立 App 数据。用单一指标评判容易以偏概全
3. **开源已成标配**：国内厂商几乎全面拥抱开源，竞争焦点从"是否开源"转向"开源质量和社区运营"
4. **产品 taste 成为分水岭**：模型能力趋同后，产品层的"taste"（删什么的能力）决定了差异化——Claude 的 Artifacts、ChatGPT 的 GPTs、智谱的 AutoGLM 都是 taste 的体现

#### 延伸思考
- **"全栈 vs 专精"路线之争**：ChatGPT/豆包/千问走全栈路线（什么都做），Claude/Kimi/MiniMax 走专精路线（编码/研究/多模态）。哪条路线更有护城河？
- **补贴获客的可持续性**：豆包、千问、元宝都在烧钱拉用户——当补贴停止后，真实留存率会是多少？
- **ToB vs ToC 的战略选择**：千问和智谱在 ToB 占优，豆包和元宝在 ToC 占优。对于 AI 对话产品，哪个市场的长期价值更高？

### Q2: 主 Chat 产品的核心价值？它和搜索、Agent、传统工具型产品的边界分别在哪里？

**考察维度：** 产品定义能力 + 对 AI 产品形态演进的理解

**Why：** 随着 Chat 产品纷纷加入搜索、Agent、工具能力，"Chat 到底是什么"这个问题变得越来越模糊。训练这道题的核心是**定义能力**——能清晰定义产品边界的人，才能做出好的产品取舍，而不是让产品变成一个什么都做但什么都不精的"万能入口"。

#### 🧠 通用思维框架：AI 产品形态边界分析法

**核心问题：这个产品形态在"确定性-不确定性"和"对话-行动"两个轴上的位置是什么？**

```
             不确定性高
                |
     Chat       |      Agent
   (对话交互)    |    (自主行动)
                |
  ──────────────┼──────────────
                |
    搜索        |     工具型产品
  (信息检索)    |    (确定性流程)
                |
             确定性高
```

**边界判断三问：**
1. 用户的目标是否明确？（明确 → 工具/搜索，不明确 → Chat）
2. 任务是否需要多步自主执行？（是 → Agent，否 → Chat）
3. 用户是否需要信源溯源？（是 → 搜索，否 → Chat）

#### 回答示例

**Chat 的核心价值 = 低门槛的智能对话交互**

本质是用自然语言降低三类成本：
- **获取信息的成本**：不需要构造精确 query，用自然语言描述就能得到答案
- **完成任务的成本**：写邮件、翻译、总结、代码生成等生产力场景
- **获得陪伴的成本**：情感交流、角色扮演、闲聊等社交/情感场景

**与其他形态的边界：**

| 维度 | Chat | 搜索 | Agent | 工具型产品 |
|------|------|------|-------|-----------|
| 核心能力 | 生成、整合、推理 | 检索已有信息 | 自主规划+多步执行 | 确定性流程 |
| 信息来源 | 模型内部知识+RAG | 索引的网页/文档 | 多工具调用 | 用户输入 |
| 容错性 | 较高（可追问修正） | 中等 | 较低（错误会链式放大） | 极低（确定性） |
| 用户控制感 | 中等 | 高 | 低 | 最高 |
| 融合趋势 | Chat + 搜索 (Perplexity) | 搜索 + 生成 | Chat 作为 Agent 入口 | 工具内嵌 Chat (Canvas) |

**关键洞察：边界正在模糊化。** Chat 正在蚕食搜索（Perplexity 模式），也在成为 Agent 的入口。产品的挑战不是"守住边界"，而是"在融合中保持核心体验的清晰度"。

#### 延伸思考
- **Chat 产品的演进路径**：纯对话 → 带工具的对话 → 带记忆的个性化助手 → Agent 入口。不同产品走到了不同阶段：ChatGPT/Claude 已进入"带工具+记忆"阶段，智谱在推 Agent，豆包仍以轻量对话为主
- **各产品的边界策略对比**：ChatGPT 走"超级应用"路线（模糊边界），Claude 走"深度协作"路线（守住编码/写作边界），Perplexity 走"Chat+搜索"融合路线
- **边界模糊时的产品策略**：让用户无感知地在 Chat/搜索/Agent 之间切换，而非让用户选择模式——Gemini 在这方面做得最自然（搜索结果直接嵌入 AI 回答）

## Part 2: 产品指标与验证

### Q3: 如果让你优化千问 App 或 PC 端的一个核心功能，你会怎么验证这个改动真的有效？

**考察维度：** 实验设计能力 + 数据驱动思维 + 对 AI 产品验证特殊性的理解

**Why：** AI 产品的验证比传统产品难得多——效果有随机性波动、用户主观感受难量化、A/B 测试在对话场景中有天然局限。这道题训练的是**实验设计思维**——能否在 AI 产品的不确定性中建立可靠的验证方法，而不是简单说"做个 A/B 测试"。

#### 🧠 通用思维框架：AI 产品改动验证三层法

**Step 1: 定义"有效"（最关键，也最容易跳过）**
- 这个功能替代了用户的什么判断或操作？
- 之前这个判断/操作是怎么被验证的？
- "有效"是指用户行为改变了，还是主观感受改善了？

**Step 2: 设计验证层次（由内到外）**

| 层次 | 方法 | 关注点 | 适用阶段 |
|------|------|--------|----------|
| **离线评测** | Testset + 自动化指标 | P95/P99 case 而非平均分 | 上线前 |
| **在线 A/B** | 分流实验 | 行为指标（采纳率、二次确认率） | 灰度期 |
| **人工评估** | Case review + 用户访谈 | 定性洞察、发现指标盲区 | 全程 |

**Step 3: 选择正确的核心指标**
- 优先选**行为指标**（用户做了什么）而非**态度指标**（用户说了什么）
- 关注**路径变化**而非**满意度评分**——用户行为路径是否因改动而偏移？

**关键自检：** "评测集是截业务切片，不是造理想样本"——你的 testset 是否覆盖了真实业务中的失败场景？

#### 回答示例

以"优化 AI 对话产品的代码生成功能"为例（适用于 ChatGPT、Claude、DeepSeek 等任何有代码能力的产品）：

1. **定义有效**：用户使用代码生成后，是否减少了手动修改的次数？核心指标 = 代码采纳率（用户直接使用生成代码的比例）
2. **离线评测**：构建 200+ 真实用户代码生成 query 的 testset，用自动化工具检测生成代码的可运行率、语法正确率
3. **在线 A/B**：灰度 10% 用户，对比代码采纳率、单次对话轮数（轮数减少可能表示一次就生成对了）、代码复制行为
4. **人工评估**：抽样 50 个 case 做专家 review，特别关注"指标显示好但实际体验差"的边角案例

**多产品案例对比**：Claude 的 Artifacts 可以直接运行代码并预览结果——这改变了"有效"的定义，从"代码正确"扩展到"用户能直接看到效果"。ChatGPT 的 Canvas 模式允许用户直接编辑生成的代码——这让"采纳率"需要细分为"直接采纳"和"编辑后采纳"。不同产品形态下，验证方法需要适配。

#### 延伸思考
- 处理"指标没动但体验变好了"：可能是指标选错了，需要回到 Step 1 重新定义"有效"
- 分人群验证：新用户 vs 老用户、技术用户 vs 非技术用户可能对同一改动有截然不同的反应
- AI 产品 A/B 的特殊难点：query 分布不均、上下文依赖、同一 query 不同时间结果不同

### Q4: 你会重点看哪些核心数据指标来判断主 Chat 做得好不好？如果留存和满意度出现冲突，你更信哪个？

**考察维度：** 指标体系设计能力 + 指标冲突时的判断力

**Why：** 这道题训练的是**指标冲突时的决策能力**。真实世界中指标经常打架，PM 需要的不是"选哪个"，而是"在什么条件下信哪个"。能否把一个看似二选一的问题拆解成有条件的判断，是 PM 思维成熟度的标志。

#### 🧠 通用思维框架：指标金字塔 + 冲突决策矩阵

**指标金字塔（由上到下）：**

```
        北极星指标
       (DAU/MAU, 周活跃对话数)
      ─────────────────
        过程指标
       (单次对话轮数, 任务完成率, 回复采纳率)
      ─────────────────────────
        质量指标
       (满意度, 幻觉率, 安全拒绝率, 响应时间)
```

**指标冲突决策框架：**

当两个指标冲突时，问三个问题：
1. **哪个是先行指标，哪个是滞后指标？** 先行指标先变化，预示未来趋势
2. **哪个更接近用户真实行为？** 行为指标 > 态度指标
3. **在当前产品阶段，哪个更重要？** 早期看留存（验证 PMF），成熟期看满意度（优化体验）

#### 回答示例

**核心指标体系：**

| 层级 | 指标 | 含义 |
|------|------|------|
| 北极星 | 周活跃对话用户数 | 比 DAU 更能反映 Chat 的真实使用深度 |
| 过程 | 单次对话轮数 | 轮数多可能是用户在深度使用，也可能是模型没有一次性解决问题——需要结合任务完成率判断 |
| 过程 | 回复采纳率 | 用户是否使用了模型的回复（复制、应用、follow-up） |
| 质量 | Thumbs up/down 率 | 直接的用户态度反馈 |
| 质量 | 幻觉率 | 通过自动化检测+抽样标注 |

**留存 vs 满意度冲突的判断：**

| 场景 | 可能原因 | 信谁 |
|------|---------|------|
| 满意度跌 + 留存没跌 | 用户有替代方案但还没迁移（你有**时间窗口**去修） | 信满意度（先行指标） |
| 留存跌 + 满意度没跌 | 满意度的度量方式可能有问题（如只采集了留下来的用户的反馈） | 信留存（行为指标） |
| 两个都跌 | 产品出了系统性问题 | 两个都信，紧急排查 |
| 两个都涨 | 恭喜，但也要警惕是否是外部因素（如竞品出问题了） | 持续监控 |

**核心观点：短期信满意度（先行指标），长期信留存（行为真相）。**

#### 延伸思考
- **生态型产品的特殊指标**：豆包需关注从抖音导流的用户 vs 自然增长用户的留存差异；元宝需关注微信生态内使用 vs 独立 App 使用的比例；Gemini 需区分 Google 搜索嵌入使用 vs 主动打开 Gemini App 的用户——不同来源的用户，留存和满意度的含义完全不同
- **满意度的采集偏差**：只有对产品有意见的人才会点 thumbs down，沉默的大多数被忽略了。Claude 的做法是在关键节点主动询问反馈，ChatGPT 则在每条回复下方提供反馈按钮
- **自检问题**："这个指标能帮我决定下一步做什么吗？"——如果一个指标涨了跌了你都不知道该做什么，那它不是好指标

## Part 3: 技术理解

### Q5: 你能简单讲一下 Transformer 的基本原理吗？为什么它比传统 RNN 更适合做大模型？

**考察维度：** 技术理解深度 + 能否用产品语言解释技术概念

**Why：** 不是要推公式，而是训练**用产品语言翻译技术概念**的能力。理解模型能力的底层逻辑，才能判断"什么是模型层面能做的，什么是产品层面需要补的"，也才能与模型团队有效沟通。

#### 🧠 通用思维框架：技术概念的产品化翻译法

**原则：用"这对产品意味着什么"来组织技术解释。**

三步法：
1. **一句话说原理**（不超过 30 字）
2. **比较优势**（为什么比替代方案好，用 2-3 个维度）
3. **产品影响**（这个技术选择如何影响产品体验）

#### 回答示例

**一句话原理：** Transformer 的核心是 Self-Attention 机制——让序列中的每个词都能直接"看到"所有其他词，而不需要按顺序逐个传递信息。

**比 RNN 好在哪（三个维度）：**

| 维度 | RNN | Transformer | 产品影响 |
|------|-----|-------------|---------|
| **并行计算** | 必须顺序处理，一个词处理完才能处理下一个 | 所有词同时处理 | 训练效率高 → Scaling Law 成为可能 → 更大的模型 = 更强的能力 |
| **长距离依赖** | 信息像传话游戏，传远了就失真（梯度消失） | 每个词直接与所有词建立连接 | 能理解长文本、保持对话一致性 |
| **可扩展性** | 增加参数不一定更好 | 更多参数 + 更多数据 = 更强（Scaling Law） | 整个大模型时代的技术基础 |

**产品语言总结：** Transformer 让"用更多算力换更强智能"这条路走通了。没有它，就没有 GPT、没有 Claude、没有整个大模型时代。

#### 延伸思考
- **KV Cache**：推理时缓存之前计算过的 Key-Value，避免重复计算——直接影响产品侧的**响应速度和首 token 延迟**。这就是为什么 Claude 和 ChatGPT 的首 token 响应越来越快
- **MoE（Mixture of Experts）**：DeepSeek、千问 Qwen3、Kimi K2 等都采用 MoE 架构，用更少的计算量激活更大的模型——DeepSeek 的极致性价比正是来源于此
- **产品意义**：当模型团队说"这个优化能降低 30% 推理成本"，PM 要能翻译成"用户感知到的响应速度能快多少"或"同等预算能服务多少更多用户"

### Q6: 你怎么理解预训练、SFT、RLHF 这几个阶段，如果少了 RLHF，产品体验会主要差在哪里？

**考察维度：** 对模型训练 pipeline 的理解 + 能否将技术阶段映射到产品体验

**Why：** 这道题训练的是**问题归因能力**——当模型效果不好时，能判断问题出在哪个训练阶段，而不是笼统地说"模型不行"。理解每个阶段的产品影响，才能给出有价值的反馈。

#### 🧠 通用思维框架：模型训练阶段 → 产品体验映射

**核心模型：每个训练阶段解决模型的一个"人格缺陷"**

| 阶段 | 类比 | 解决什么问题 | 没有它会怎样 |
|------|------|-------------|-------------|
| **预训练** | 读遍所有书 | 获得知识和语言能力 | 什么都不会，只会输出随机文本 |
| **SFT** | 学会按指令回答 | 从"续写文本"变成"回答问题" | 会写但不会对话，像一本自动翻页的书 |
| **RLHF** | 学会什么回答是"好"的 | 对齐人类偏好和价值观 | 会对话但"不懂事"（见下文） |

**产品启示：** 当你发现模型效果不好时，判断问题属于哪个阶段：
- 知识错误 → 预训练数据问题
- 格式混乱/不按指令来 → SFT 问题
- 回答"正确但不好" → RLHF 问题

#### 回答示例

**少了 RLHF，产品体验会差在哪里？**

1. **啰嗦且缺乏结构**：不知道用户喜欢什么样的回答长度和组织方式，倾向于堆砌所有相关信息
2. **不会拒绝**：缺乏安全对齐，对有害/敏感请求照单全收
3. **"正确但无用"**：事实可能准确，但不是用户想要的角度、深度或风格——比如用户问"怎么做番茄炒蛋"，模型从番茄的生物学分类开始讲起
4. **缺乏"人味"**：机械地堆砌信息，而非有逻辑、有节奏地组织回答

**本质洞察：** RLHF 不是在教模型"新知识"，而是在教模型"产品判断力"——什么该说什么不该说、先说什么后说什么、详细说还是简洁说。**没有 RLHF 的模型就像一个百科全书式的学者，知识渊博但完全不懂社交。**

#### 延伸思考
- **DPO（Direct Preference Optimization）**：RLHF 的替代方案，省掉了训练 Reward Model 的步骤，直接从偏好数据学习——降低了训练成本和复杂度
- **PM 在 RLHF 中的角色**：定义标注规范（什么是"好回答"的标准）、设计偏好数据采集策略（收集什么样的 A/B 对比数据）、审核 Reward Model 的表现（奖励信号是否对齐用户价值）
- **RLAIF（用 AI 代替人类做 feedback）**：降低标注成本，但需要解决"AI 偏好 ≠ 用户偏好"的问题。Anthropic 在这方面做了大量研究（Constitutional AI），这也是 Claude 安全对齐领先的原因之一
- **对比各产品的 RLHF 侧重**：ChatGPT 侧重通用对齐，Claude 侧重安全和诚实，DeepSeek 侧重推理链质量——不同的 RLHF 策略直接塑造了不同的产品"性格"

### Q7: 你怎么理解 prompt、system prompt、上下文窗口、RAG、Agent 这些概念？它们分别更适合解决哪一类问题？

**考察维度：** 产品侧技术概念的系统性理解

**Why：** 这些是 AI PM 日常工作中每天都要用到的概念。训练重点不是"能不能背定义"，而是"能不能用它们做产品决策"——比如什么时候该用 RAG 而不是扩大上下文窗口，什么时候该用 Agent 而不是多轮对话。

#### 🧠 通用思维框架：AI 产品技术栈的分层理解

**统一视角：这五个概念都在解决同一个核心问题——"如何让模型在正确的上下文中给出正确的回答"。**

```
┌─────────────────────────────────────┐
│           Agent（行动能力）           │  解决：需要多步执行的任务
│  ┌───────────────────────────────┐  │
│  │        RAG（外部知识）          │  │  解决：模型不知道的事 + 时效性
│  │  ┌─────────────────────────┐  │  │
│  │  │    上下文窗口（容量）      │  │  │  限制：一次能看多少信息
│  │  │  ┌───────────────────┐  │  │  │
│  │  │  │ System Prompt（人设）│ │  │  │  定义：你是谁、怎么答
│  │  │  │  ┌─────────────┐  │  │  │  │
│  │  │  │  │ Prompt（输入 │  │  │  │  │  定义：用户问什么
│  │  │  │  └─────────────┘  │  │  │  │
│  │  │  └───────────────────┘  │  │  │
│  │  └─────────────────────────┘  │  │
│  └───────────────────────────────┘  │
└─────────────────────────────────────┘
```

**决策树：什么时候用什么？**
- 用户问题在模型知识范围内？ → Prompt + System Prompt 就够
- 需要外部/最新信息？ → 加 RAG
- 单次回答装不下？ → 需要更大的上下文窗口或摘要策略
- 需要执行操作（查数据库、发邮件、调 API）？ → 需要 Agent

#### 回答示例

| 概念 | 是什么 | 解决什么问题 | 产品侧 trade-off |
|------|--------|-------------|------------------|
| **Prompt** | 用户输入 | 定义"问什么" | 用户表达能力差异大，需要产品引导 |
| **System Prompt** | 产品预设的行为规范 | 定义"你是谁、怎么答" | 太长会挤占上下文窗口；太短会缺乏约束 |
| **上下文窗口** | 模型一次能看的信息量上限 | 决定对话深度的天花板 | 窗口越大成本越高、推理越慢 |
| **RAG** | 从外部知识库检索信息注入上下文 | 模型不知道的事 + 信息时效性 | 检索质量直接决定回答质量（garbage in, garbage out） |
| **Agent** | 模型 + 工具 + 规划能力 | 需要多步执行才能完成的任务 | 自主性 vs 可控性的矛盾——Agent 越自主，出错时的影响越大 |

**它们的关系：** Prompt 和 System Prompt 在上下文窗口内；RAG 是从外部"注入"信息到上下文窗口；Agent 在对话之上加了行动能力，可以调用工具、执行代码、访问数据库。

#### 延伸思考
- **产品决策案例**："帮我查一下最近的股价"——该用 RAG（检索金融数据）还是 Agent（调用 API）？ChatGPT 的做法是通过 Plugin/GPTs 调用金融 API（Agent 路线），Perplexity 则通过实时搜索注入上下文（RAG 路线）。答案取决于是否需要实时数据和精确数值
- **各产品的上下文窗口策略对比**：Claude 1M tokens（最大）、Gemini 1M、Kimi 200 万字、ChatGPT 128K。更大的窗口意味着更高的成本——Kimi 选择把长文本作为核心卖点，愿意为此付出成本；而 ChatGPT 选择用 RAG+摘要在较小窗口内解决问题
- **System Prompt 的产品设计挑战**：如何在有限的窗口内平衡"人设定义""行为约束""安全规则"——Claude 的 system prompt 以安全规则著称，ChatGPT 的 Custom Instructions 让用户参与定义

## Part 4: 产品设计与策略

### Q8: 如果用户一句话里有多个意图，或者表达很模糊，你会怎么做意图识别和回复策略设计？

**考察维度：** 对话系统设计能力 + 产品策略思维

**Why：** 这是 Chat 产品日常面对的最核心问题之一。用户不会像调用 API 一样给你格式化的输入。这道题训练的是**对话系统设计思维**——能否建立系统性的意图处理策略，而非"遇到模糊就追问"这种简单粗暴的方案。

#### 🧠 通用思维框架：用户意图三分法 + 回复策略矩阵

**先分类，再决策：**

| 类型 | 定义 | 例子 |
|------|------|------|
| **多意图** | 一句话里包含多个明确请求 | "帮我翻译这段话，然后总结要点" |
| **模糊意图** | 请求不够具体，缺乏关键信息 | "帮我写个东西" |
| **隐含意图** | 表面请求背后有真实需求 | "明天天气怎么样"（可能是在决定出行） |

**回复策略决策树：**

```
用户输入
  ├─ 意图明确且单一 → 直接回答
  ├─ 多意图
  │   ├─ 意图间有依赖 → 串行处理（先翻译再总结）
  │   └─ 意图间无依赖 → 结构化并行回答（分点）
  ├─ 模糊意图
  │   ├─ 高置信度猜测 → 给最可能的答案 + 提供替代理解
  │   └─ 低置信度 → 追问（但控制在 1-2 轮）
  └─ 隐含意图
      └─ 回答表面问题 + 主动补充可能的深层需求
```

**核心原则：降低用户的表达成本。系统适应用户，而非让用户适应系统。**

#### 回答示例

**多意图场景**："帮我把这段英文翻译成中文，然后用更简洁的语言重新写一遍"
- 策略：识别两个意图有依赖关系（先翻译才能重写），串行处理，输出中用分段清晰标注每个步骤的结果

**模糊意图场景**："帮我写个东西"
- 差的做法：追问"你要写什么？格式是什么？给谁看的？长度要求？"（一连串追问让用户崩溃）
- 好的做法："我可以帮你写！你是想写一封邮件、一份报告，还是其他类型的文档？简单告诉我主题和受众就行。"（一次追问，给出选项降低用户思考成本）

**隐含意图场景**："Python 的 list 和 tuple 有什么区别？"
- 表面：解释数据结构差异
- 隐含：用户可能在做选择（该用哪个）
- 好的做法：先简要解释区别，然后主动补充"如果你是在选择用哪个，通常的原则是……"

#### 延伸思考
- **用户历史做意图先验**：ChatGPT 的 Memory 和 Claude 的 Projects 都在尝试通过用户画像提升意图识别准确度。如果用户连续 3 次对话都在问代码问题，第 4 次说"帮我看看这个"，大概率是代码相关
- **各产品的意图处理策略对比**：ChatGPT 倾向于直接给出最可能的答案（错了用户纠正），Claude 更倾向于先确认再回答。豆包在角色扮演场景下几乎不追问，直接进入角色——不同场景需要不同的策略
- **意图识别的产品化**：不是让模型自己猜，而是通过产品设计降低模糊度——Kimi 的推荐 prompt、ChatGPT 的 GPTs 入口、智谱的 Skills 分类，都是在产品层面解决意图模糊问题

### Q9: 你如何理解上下文、短期记忆、长期记忆的区别？什么信息应该记住，什么信息不该记住，为什么？

**考察维度：** 记忆系统设计能力 + 隐私边界意识

**Why：** 记忆是 Chat 产品下一阶段的**核心差异化能力**。目前大部分产品的记忆功能都很初级，谁先做好谁就有竞争优势。这道题训练的是**记忆系统的产品设计思维**——不只是"记住用户偏好"这么简单，还涉及隐私、信任、数据衰减等复杂问题。

#### 🧠 通用思维框架：三层记忆模型 + 记忆决策矩阵

**三层记忆：**

| 层级 | 范围 | 生命周期 | 存储方式 |
|------|------|----------|----------|
| **上下文** | 当前对话窗口内的信息 | 对话结束即消失 | 在上下文窗口中 |
| **短期记忆** | 跨对话但有时效的信息 | 天/周级别，会衰减 | 结构化摘要 |
| **长期记忆** | 持久化的用户画像和偏好 | 持久化，手动删除 | 结构化数据 |

**记忆决策矩阵——什么该记、什么不该记：**

| 信息类型 | 该记？ | 原因 |
|----------|--------|------|
| 用户明确告知的偏好（"我喜欢简洁回答"） | ✅ 长期 | 直接提升个性化体验 |
| 反复出现的使用模式（总是问代码问题） | ✅ 长期 | 可以主动优化回答风格 |
| 用户身份/职业（"我是产品经理"） | ✅ 长期 | 影响回答的深度和角度 |
| 当前任务上下文（"我在准备周报"） | ✅ 短期 | 本周有用，下个月无用 |
| 一次性查询（"1美元等于多少人民币"） | ❌ | 无持久价值 |
| 敏感信息（密码、身份证号） | ❌ | 隐私风险 |
| 情绪化表达（"我今天心情不好"） | ⚠️ 短期 | 当次对话有用，但不应长期标签化用户 |

#### 回答示例

**记忆系统的四个设计原则：**

1. **可感知**：用户知道你记了什么（ChatGPT 的 Memory 面板）
2. **可控制**：用户能查看、修改、删除记忆
3. **渐进式建立**：不要一上来就问一堆用户信息，通过多次对话自然积累
4. **衰减机制**：过时信息自动降权（用户三个月前说"我在准备考研"，现在可能已经考完了）

**竞品对比：**

| 产品 | 记忆方式 | 优点 | 缺点 |
|------|---------|------|------|
| ChatGPT Memory | 自动提取 + 用户可编辑 | 透明、可控 | 提取质量不稳定，有时记错 |
| Kimi | 对话历史搜索 | 简单直接 | 不是真正的记忆，只是搜索 |
| Claude | 跨对话 memory | 结构化存储 | 需要用户主动告知 |

#### 延伸思考
- **记忆冲突处理**：如果用户两个月前说"我是学生"，今天说"我在公司做项目"——是更新还是保留两条？ChatGPT Memory 会保留两条并标注时间，Claude 倾向于用最新信息覆盖旧信息
- **记忆的存储形式**：结构化数据（key-value）vs 自然语言摘要——各有优缺点。ChatGPT 用自然语言摘要，Claude Code 用结构化 markdown 文件（有 frontmatter 和类型分类）
- **隐私的产品化**：记忆功能的最大障碍不是技术，而是**用户信任**——一个让用户感到"被监视"的记忆系统，不如没有。这也是为什么 Claude 选择让记忆功能需要用户主动触发，而非完全自动化

### Q10: 如果模型出现幻觉，你会怎么判断是模型能力问题、检索问题、prompt 问题还是产品策略问题？

**考察维度：** 问题诊断能力 + 系统性思维

**Why：** 这道题训练的是**系统性问题诊断能力**。模型出了问题，能否快速定位原因并给出方向？"模型幻觉了，让模型团队修"是甩锅式反馈，对团队毫无价值。AI PM 需要能拆解到具体层级。

#### 🧠 通用思维框架：幻觉归因四层模型 + 控制变量排查法

**四层归因（由底向上排查）：**

```
┌──────────────────────────────────┐
│  Layer 4: 产品策略问题             │  产品没有在合适时机设置兜底
├──────────────────────────────────┤
│  Layer 3: Prompt 问题             │  System prompt 指令不清晰/冲突
├──────────────────────────────────┤
│  Layer 2: 检索问题（RAG）          │  检索到了错误/不相关的文档
├──────────────────────────────────┤
│  Layer 1: 模型能力问题             │  模型本身知识缺失或推理错误
└──────────────────────────────────┘
```

**控制变量排查法：**

| 操作 | 如果幻觉消失 | 说明 |
|------|-------------|------|
| 换一种 prompt 问同一个问题 | ✅ 消失 | → Prompt 问题 |
| 同一个 prompt 问不同问题 | ✅ 消失 | → 特定知识领域的模型能力问题 |
| 关闭 RAG 再问 | ✅ 消失 | → 检索注入了错误信息 |
| 开启 RAG 再问 | ✅ 消失 | → 模型知识缺失，RAG 补齐了 |
| 以上都试了还幻觉 | — | → 模型能力的系统性问题，或产品策略需要兜底 |

#### 回答示例

**实际案例拆解：**

假设某 AI 对话产品回答"杭州市的人口是 500 万"（实际约 1200 万），如何排查？

1. **换 prompt**：问"杭州有多少人口？" vs "请告诉我杭州市最新的常住人口数据" → 如果后者回答正确，说明是 prompt 不够精确
2. **关闭 RAG**：如果关闭后回答变成"约 1000 万"（更接近但不精确），开启后反而错误 → 说明 RAG 检索到了过时或错误的数据源
3. **测试同类问题**：问其他城市人口 → 如果都不准，说明是模型在人口数据这个领域的能力系统性不足
4. **产品策略层面**：模型是否给出了不确定性信号（如"大约""据我了解"）？产品有没有引导用户去权威数据源确认？

#### 延伸思考
- 建立**幻觉 case 分类库**：按领域（数学/事实/逻辑/代码）和原因（知识缺失/推理错误/检索污染/prompt 歧义）分类，积累后可以发现系统性问题
- **各产品的幻觉应对策略对比**：Perplexity 强制展示 citation 来源；Claude 在不确定时会主动说"我不确定"；ChatGPT 的 browsing 模式会标注信息来源；DeepSeek 的 R1 通过展示推理链让用户看到思考过程——不同的产品策略反映了不同的安全哲学
- **产品策略兜底**：即使不能消除幻觉，也可以通过产品设计降低幻觉的伤害——citation 展示来源、置信度标识、引导用户二次确认

### Q11: 你会怎么评估一个 AI 对话系统答得好不好？除了人工判断，还可以看哪些技术或算法指标？

**考察维度：** 评估体系设计能力——这是 AI PM 的核心差异化能力

**Why：** 人工评估成本高、不可 scale、有主观偏差。这道题训练的是**评估体系设计能力**——如何建立自动化评估体系，以及理解"没有单一指标能衡量好不好"这个核心认知。这是 AI PM 区别于传统 PM 的最关键能力之一。

#### 🧠 通用思维框架：AI 对话评估五维模型 + 自动化指标分类

**五维评估模型：**

| 维度 | 评估什么 | 核心问题 |
|------|---------|---------|
| **事实准确性** | 回答是否正确 | "它说的是真的吗？" |
| **指令遵循度** | 是否按要求回答 | "它做了我让它做的事吗？" |
| **回答质量** | 结构、可读性、完整性 | "回答好不好读、好不好用？" |
| **安全性** | 是否输出有害内容 | "它有没有说不该说的？" |
| **用户满意度** | 用户的主观评价 | "用户觉得好吗？" |

**自动化指标分类：**

| 维度 | 自动化指标 | 怎么用 |
|------|-----------|--------|
| 事实准确性 | NLI 模型检测回答与 source 的一致性；实体级 fact-checking | 批量跑，快速发现事实性错误 |
| 指令遵循度 | 格式匹配率（如"用 200 字回答"是否遵守）；约束条件满足率 | 规则化检测，容易自动化 |
| 回答质量 | Perplexity（流畅度 proxy）；回答长度分布；**LLM-as-judge**（用另一个模型评分） | LLM-as-judge 是目前最实用的自动化质量评估方案 |
| 安全性 | 安全分类器检测有害内容；拒绝率分布 | 关注是否过度拒绝（误杀） |
| 满意度 | **行为代理指标**：追问率（可能不满）、复制/分享（有用）、thumbs up/down | 用行为代替态度，更客观 |

**核心认知：关注 P95/P99 的极端 case，而非平均分。** 平均分 4.5 的系统可能在 5% 的 case 上表现极差，而那 5% 才是用户流失的原因。

#### 回答示例

**构建评估体系的步骤：**

1. **建立 eval set**："从真实业务链路中截取失败 case"——不是人工编造理想样本，而是收集线上真实的 bad case
2. **分维度设计指标**：每个维度至少一个自动化指标 + 一个人工评估维度
3. **设置基线**：用当前版本的表现作为 baseline，新版本必须在每个维度都不退化
4. **持续监控**：不是上线前评一次就完了，而是持续监控线上表现

**LLM-as-judge 的实用方案：**
- 用 GPT-4 级别的模型对回答打分（1-5 分），prompt 中给出评分标准
- 优点：成本远低于人工，可大规模使用
- 局限：评估模型本身有偏差（倾向于给长回答高分、对自己生成的内容评分更高）

#### 延伸思考
- **Interleaving 方法**：A/B 测试的升级版——在同一个对话中交替展示两个模型的回答，让用户选择更好的，消除了 query 分布不均的问题。ChatGPT 内部大量使用此方法对比模型版本
- **行业评测的局限性**：LMSYS Chatbot Arena 是目前最权威的众包评测，但它偏向英文、偏向"有趣"而非"有用"。国内的 SuperCLUE 等评测在中文场景更有参考价值，但样本量和覆盖面有限
- **评估的自检问题**："这个评估结果能帮我决定下一步做什么吗？"——如果评估分高了低了你都不知道该改什么，说明评估维度太粗，需要拆解

### Q12: 如果让你在两周内做一个能明显提升主 Chat 体验的小改动，你会做什么？如果研发资源非常有限，你会怎么取舍？

**考察维度：** 产品 sense + 优先级判断力 + 落地执行力

**Why：** 这道题训练的是**约束条件下的优先级判断力**。"我要做一个全新的记忆系统"——那不是两周能做的事。能在有限资源下做出高 ROI 的决策，而不是画大饼，才是 PM 的核心能力。

#### 🧠 通用思维框架：约束条件下的产品决策三维评分法

**决策矩阵：影响面 × 改动成本 × 可验证性**

| 维度 | 高分 | 低分 |
|------|------|------|
| **影响面** | 影响大部分用户的高频场景 | 只影响少数边缘用户 |
| **改动成本** | 纯前端/配置/prompt 层面 | 需要改模型/改架构 |
| **可验证性** | 两周内能看到数据变化 | 效果需要数月才能体现 |

**自检问题（taste 框架）：** "这个改动做完，用户能一句话说出产品变了什么吗？" 如果说不出来，可能不值得做。

**取舍原则：优先做"改动小但用户感知大"的事。**

#### 回答示例

**高 ROI 候选方向（按可行性排序）：**

| 方向 | 改动成本 | 用户感知 | 可验证指标 |
|------|---------|---------|-----------|
| **优化 system prompt**（减少啰嗦、提高结构化） | 零研发，纯 prompt 调优 | 中高 | 回答长度分布、采纳率 |
| **优化回复格式呈现**（代码高亮、markdown 渲染、分点回答的交互优化） | 纯前端 | 高 | 复制率、停留时间 |
| **增加推荐追问**（回复后推荐 2-3 个 follow-up 问题） | 前端 + 简单后端 | 高 | 对话轮数、留存 |
| **增加回复反馈机制**（like/dislike + 原因分类） | 前端 + 数据管道 | 中 | 反馈率、RLHF 数据量 |

**我的选择：优化 system prompt + 推荐追问（组合拳）**

理由：
1. System prompt 优化**零研发成本**，第一周就能完成 A/B 测试
2. 推荐追问**用户感知强**，且直接提升对话深度和留存
3. 两者组合可以在两周内完成端到端验证

**两周排期：**
- W1：System prompt 优化（3 天调优 + 2 天 A/B）+ 推荐追问需求定义和开发
- W2：推荐追问灰度上线 + 两个改动的数据验证 + 复盘文档

#### 延伸思考
- **反馈机制的长期价值**：虽然短期用户感知不强，但它是 RLHF 数据飞轮的起点——每一次 thumbs down 都是免费的训练数据。ChatGPT 和 Claude 已经证明了这个飞轮的威力
- **各产品的"小改动大效果"案例**：ChatGPT 的推荐追问（显著提升对话深度）、Claude 的 Artifacts（让代码/文档可直接预览和编辑）、Kimi 的探索版（深度思考模式）——这些都是改动相对小但用户感知极强的产品决策
- **如果只能做一个**：选 system prompt 优化，因为零成本且可快速验证，是典型的"高杠杆小改动"。这个思路适用于任何 AI 对话产品

### 分析通用原则

1. **先说结论，再展开** — 结构化表达的第一原则
2. **用具体 case，不用抽象概念** — "比如用户问 XXX 时……"比"在模糊意图场景下……"有力 10 倍
3. **敢说"我不确定，但我会这样验证"** — 比假装什么都知道更有深度
4. **多产品对比而非单一视角** — 用多个产品的做法对比分析，展示行业全局视野
5. **暴露思维过程** — 分析的价值不只在结论，更在于得出结论的逻辑链
